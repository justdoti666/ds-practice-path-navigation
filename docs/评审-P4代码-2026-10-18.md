## 2. 问题清单

### 高

**H1 · 画布不认 `sid` 字段 → 与我们 P1/P2 的 `Station` 不兼容（实测抛异常）**

- 位置：`ui/canvas.py::_as_station_id`（约 327–342 行）。
- 现象：只识别 `id / station_id / station`，我们 P2 的 `Station(sid, name, x, y)` 没有这些字段。
- 证据（探针）：`_as_station_id(OurStation("S1",…)) == ''` ⇒ `normalise_graph()` 抛
  `ValueError: 图对象里没有站点（stations 为空），无法绘制。`
- 为什么重要：`docs/交接/P1-收到的口径.md` 与《技术方案》§6 都把 `Station` 写成 `sid`；一旦把两套 `core` 合并，画布会**整体不可用**。
- 建议：`_as_station_id` 增加 `"sid"`（1 行）；`normalise_graph` 对 dict 形式的 `stations` 允许用 key 当 id；补一条单测。

**H2 · `normalise_result` 对 `events` 的兼容声明不成立（动画静默失效）**

- 位置：`ui/canvas.py::normalise_result`（约 543–550 行）与 `_as_station_id`（约 333 行）。
- 现象：docstring 声称兼容任务书接口的 `events`；但任务书/我们 P2 的 `events` 是 `[("settle", sid), …]`，
  `_as_station_id(("settle","S1"))` 取 `item[0]` ⇒ `"settle"`。
- 证据（探针）：`view.events == ['settle', 'settle', 'settle']`；动画阶段会尝试点亮不存在的站，**不报错但动画形同虚设**。
- 建议：对 tuple/list 事件先判 `kind in {"settle","visit","push"}` 再取 `item[1]`；或明确只支持 `visited_order` 并在 docstring 删掉 `events` 承诺。补单测。

### 中

**M1 · 缺少"距离权重"，且无法表达快线 → 任务书 P01 的多准则口径没落地**

- 位置：`core/algorithms.py::dijkstra`（只用 `edge.time`）、`core/graph.py:62`（全局 `speed_kmh=35`）。
- 任务书 P01 原文：**"最快路径：基于距离/时间权重的 Dijkstra"**。
- 现状：只有时间权重；所有线路同一速度 ⇒ 无法表达"快线 vs 接驳线"，也就做不出"最快 ≠ 最短"的对比（我们 P2 用 S4→S11 证明了这种差异，他们的数据模型表达不了）。
- 证据：docx 全文中"距离权重/时间权重"各 **0 次**；他们的草稿已诚实写明"算法只支持时间/换乘两种准则"（`docs/P4-报告章节草稿.md:188`），但**终稿没有保留这句局限**。
- 建议：二选一 —— ① 数据层支持 per-line `speed_kmh` + `weight ∈ {time, distance}`（约 40 行，最贴合任务书）；② 时间不够就把"仅时间/换乘两准则"明确写进终稿第 3/5 章。

**M2 · BFS 的 `expanded` 与 `visited_order` 不是最终路径那次搜索的（口径不可横比）**

- 位置：`core/algorithms.py:454–462`：`expanded` 来自分层 BFS，最终路径来自第二次 `_fastest_within_transfers`。
- 后果 1：三算法对比表横比"扩展节点"会失真（BFS 只有 2–5）；报告里"BFS 扩展最少"没有意义。
- 后果 2：动画的搜索波（BFS `visited_order`）与最终高亮路径**可能不同源**，与"动画与结果一致"的承诺有缝。
- 证据：`tools/bench.py` 输出 BFS 扩展 5/4/2/3，而同对起终点 Dijkstra 151/143/112/114。
- 建议：BFS 的 `expanded` 改成"两次搜索之和"或明确标注"分层 BFS 的线路扩展帧"；报告表格给 BFS 单列注脚；若动画承诺一致，则 `visited_order` 用第二遍搜索的（或干脆用最终路径补）。

**M3 · 报告的结论与自己给出的数据矛盾**

- 位置：`reports/城市交通路径导航系统_实验报告.docx` 4.6 节结论句（以及 `tools/make_report.py` 的生成模板）。
- 原文：*"扩展节点均值：Dijkstra 133.0，A\* 76.8，BFS 3.6。A\* 借助直线距离启发函数，平均搜索规模最小。"*
- 矛盾：BFS 的 3.6 **比 A\* 的 76.8 更小**，所以"A\* 最小"是错的。
- 证据：我用他们的 `bench.py` 复跑，数值与报告一致（133.0/76.8/3.6），说明不是数据问题，是**结论句写错**。
- 建议：改成"A\* 在**可比的两种最短路算法**中扩展最少（相对 Dijkstra −42%）"；BFS 单列并说明单位不同。

**M4 · `tools/bench.py` 默认覆盖入库产物，复跑即让报告闸门变红**

- 位置：`tools/bench.py` 默认输出 `docs/bench.csv`（并回写 `docs/bench.md`）。
- 现象（我亲自踩到）：复跑一次 bench ⇒ `docs/bench.csv` 被改成新数值（0.16/0.15/0.17…），
  `python tools/check_report.py` 立刻 **20/22 红**（"表 4-3 与 bench.csv 不一致"、"4.6/4.7 关键数字缺失"）。
  还原（`git checkout -- docs/bench.csv docs/bench.md`）后 **22/22 绿**。
- 建议：默认输出到 `_smoke/bench.csv`（不入库），加 `--update-docs` 才写 `docs/`；或让 `check_report.py` 在比较前先重跑 bench。

## 3. 亮点（值得保留的做法）

1. **分层干净**：`core`（P1/P2 只读）/ `ui`（画布）/ `tools`（工程化）三层，`canvas.py` 不 import `solver`，窗口除 L3 一处外只调画布公开 API。
2. **测试有判别力**：10 项自检 + 35 个接口用例 + 3 种 mutation 全 CAUGHT —— 这是"断言不是恒真"的硬证据，比"测试全绿"有说服力得多。
3. **渲染细节扎实**：等比适配 + y 翻转 + 缩放锚点（数学正确，自检 09 验证）、`_RectIndex` 做标签避让（134 站只画 121 个、零重叠）、命中半径 ≤12 px、动画批帧 ≤36 帧、导出 PS/PNG、Windows DPI 适配。
4. **工程化完整**：CI（xvfb 下跑 GUI + mutation）、CODEOWNERS/PR/Issue 模板、`prepare_github.py --check` 自带仓库体检（0 阻塞）、错误码表、SDK/CLI/HTTP 三形态接口、`check_report.py` 22 项报告闸门。
5. **数据与校验**：134 站 × 7 线，JSON/TXT 双格式实测等价；校验覆盖站名重复、环线站数、参数范围、线路引用。
